## Diff 机制分析

问题：Standby NameNode 的 EditLogTailer 在一个 tailing 周期内**持有 FSNamesystem 写锁应用整个 journal segment**。写锁粒度粗，standby 上的读请求（client 经 `ha.enable.standby.reads` 或 JMX/metrics 读）在 segment 应用期间被长时间阻塞。改动：

1. **FSEditLogLoader**：`loadFSEdits` / `loadEditRecords` 签名增加 `long maxTxnsToRead` 参数；`loadEditRecords` 的循环每应用一笔事务就 `numEdits++` 并检查 `if (numEdits >= maxTxnsToRead) break;`，从而把"读多少笔"变成可控上限。默认 `Long.MAX_VALUE` 时行为与原来一致。
2. **FSImage**：`loadEdits(Iterable, FSNamesystem, long maxTxnsToRead, StartupOption, MetaRecoveryContext)` 由 private 改 public，把 maxTxnsToRead 透传给 loader；NN 启动加载路径传 `Long.MAX_VALUE`（不受限）。附带修复：原来 `if (editIn.getLastTxId() != INVALID_TXID) lastAppliedTxId = editIn.getLastTxId();` 无条件快进 lastAppliedTxId——加了 `&& recovery != null` 条件，避免非 recovery 模式下提前跳过未应用的事务（这是 tailing 场景下的正确性修正）。
3. **EditLogTailer**：新增配置
   - `dfs.ha.tail-edits.max-txns-per-lock`（`DFS_HA_TAILEDITS_MAX_TXNS_PER_LOCK_KEY`）
   - 默认值 `Long.MAX_VALUE`（即默认行为不变，保持整个 segment 一把锁）。
   `doTailEdits()` 中 `image.loadEdits(streams, namesystem, maxTxnsPerLock, null, null)`。由于 `doTailEdits` 本身在 `namesystem.writeLockInterruptibly()` 内调用 loadEdits，而 `loadEditRecords` 内部也独立 `fsNamesys.writeLock()`，设置上限后每次只应用 maxTxnsPerLock 笔就返回释放锁，tailer 线程下一轮 sleep/周期再续——写锁被切成小段，standby 读得以穿插。
4. 测试：`TestEditLogTailer.testTailer` 设 `max-txns-per-lock=3`，并断言 standby 的 lastAppliedTxId 与 active lastWrittenTxId 一致（验证分批应用不丢事务）。

## 对 RPC 性能的影响评估

**中**（有条件）。

- 默认配置（`Long.MAX_VALUE`）下零行为变化，零收益——这是纯 opt-in 改进。
- 开启 `dfs.ha.tail-edits.max-txns-per-lock`（如设为几千）后，对 standby NameNode 的**读 RPC 延迟尾延迟**有实质改善：高写负载下 tailing 一批 segment 可能持写锁数百毫秒甚至秒级，分批后 standby 读（client 读、JMX）卡顿明显降低。对 active NN RPC 无影响。
- 附带修复的 `lastAppliedTxId` 快进 bug 提升 tailing 正确性。
