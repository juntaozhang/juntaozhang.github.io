# HDFS-15211 — EC: File write hangs during close in case of Exception during updatePipeline

## Commit

- **Hash**: `a3224ff799b59e75dc50890c4b49b7113e57a53c`（branch-3.1，首次发布于 3.1.4）
- **Author**: Surendra Singh Lilhore（代码贡献者 Ayush Saxena）
- **Date**: 2020-03-15
- **涉及文件**:
  - `hadoop-hdfs-project/hadoop-hdfs-client/src/main/java/org/apache/hadoop/hdfs/DFSStripedOutputStream.java`（+32/-22）

## Diff 机制分析

**根因**：EC 写（DFSStripedOutputStream）有两处"失败 streamer 数超过 parity 块数
（numAllBlocks - numDataBlocks）即判定不可恢复"的检查（`checkStreamers()` 和
`checkStreamerFailures()`），原实现是**直接 `throw new IOException(...)`**，
但此时各个 `StripedDataStreamer` 线程还活着且处于阻塞等待状态：

1. 抛出异常后 streamer 没有被关闭，仍 park 在队列上等 packet/等 ack；
2. 应用层收到异常后调用 `close()`（try-with-resources 典型路径），
   `closeImpl()` 走 flush 路径去 join 这些 streamer；
3. streamer 永远不会完成 → `close()` 永远不返回 → **文件写挂死在 close**。

JIRA 描述："the streamers won't be having any result due to exception, and the
streamers will stay stuck, so the write hangs during file close"。

**修复方式**：

1. 两处"不可恢复"检查在 throw 之前新增 `closeAllStreamers()`：
   遍历所有 streamer 调 `streamer.close(true)`（内部走 setClosed/唤醒机制），
   让线程从 park 中退出，保证后续 close/flush 的 join 能完成。
2. `closeImpl()` 结构调整：把 `isClosed()` 的快路径检查**移进 try 块**，
   使快路径抛出的 `exceptionLastSeen.check(true)` / MultipleIOException
   也经过与慢路径一致的异常清理逻辑，避免异常路径下资源/线程泄漏。
   （原有逻辑是快路径在 try 之外提前 return，异常语义与慢路径不一致。）

## JIRA 页面信息

- **Affects Version/s**: **3.1.1**, 3.2.1, 3.3.0（EC 写路径 3.1.1 明确在列）
- **Fix Version/s**: **3.1.4**, 3.2.2, 3.3.0
- **Priority**: **Critical**
- **报告人/Assignee**: Ayush Saxena（2020-03-06 创建，03-15 解决；补丁迭代 5 版，
  附两个线程 dump 展示挂死栈）
- **触发场景**：EC 文件写过程中某 DN 慢/故障导致 close 慢 streamer，期间
  updatePipeline 又抛异常，失败 streamer 数超过 parity 块数（如 RS-6-3 下超过 3）
  → 判定不可恢复 → 但 close() 挂死。即"写已经失败，但客户端既拿不到异常也关不掉流"。

## 影响评估

**高**（对使用 EC 的集群）/ 低（不使用 EC 的集群完全不涉及）。

- 影响 HDFS 客户端：挂死点在 `close()`，应用线程（以及 try-with-resources 的
  隐式 close）无限阻塞，比直接抛异常恶劣得多——作业框架表现为 task 挂死。
- Affects Version 明确包含 3.1.1，EC 用户在 DN 抖动 + 慢节点场景可触发；
  Priority Critical，社区评估为必须修复。
- 与 HDFS-15219 叠加时（Error 挂死 + close 挂死），EC 写客户端的故障
  收敛能力在 3.1.1 上整体偏弱。

## 是否值得 cherry-pick 到 3.1.1

**值得（使用 EC 则强烈建议）**。

- 单文件改动，经 `git apply -3` 实测**干净应用**到 3.1.1，无冲突。
- 无服务端改动、纯客户端失败路径收敛，回归风险低。
- 不使用 Erasure Coding 的集群可不 pick；EC 生产集群应随 HDFS-15219 一起 pick。
