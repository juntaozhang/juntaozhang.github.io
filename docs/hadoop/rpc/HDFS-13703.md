## Diff 机制分析

改动对象是 `DFSUtilClient.CorruptedBlocks`（客户端读路径上用于收集损坏 block 副本的容器）：

1. **改动前**：`CorruptedBlocks` 构造时无条件 `new HashMap<>()`；每次 `DFSInputStream` 读 block（`readBlock`/`blockSeekTo` 等路径）都会 new 一个该对象 + 一个 HashMap，即使读完全成功、一个 corrupt block 都没遇到。
2. **改动后**：`corruptionMap` 字段默认保持 `null`，延迟到 `addCorruptedBlock()` 第一次真正遇到损坏块时才分配 HashMap。`getCorruptionMap()` 的调用方（`DFSInputStream.reportCheckSumFailure` 和 `DataNode.reportCorruptedBlocks`）把判空从 `isEmpty()` 改为 `== null`。
3. 这是一个**纯客户端读路径**的对象分配优化，每次 block 读取少一次 `CorruptedBlocks` + `HashMap` 两个对象分配。

**重要纠正**：之前有人说这是 "NN block report 热路径优化"——这不准确。Block report 路径（`BlockManager` / `StorageBlockReport`）与此改动无关；`DataNode.reportCorruptedBlocks` 只在 checksum 校验失败后才被调用，不是常规 block report 路径。真实的受益方是**数据读取热路径**（`DFSInputStream` 每次 `readBlock`），属于客户端 GC 压力优化，与 NameNode RPC 无关。

## JIRA 页面信息

- **标题**: Avoid allocation of CorruptedBlocks hashmap when no corrupted blocks are hit
- **类型/优先级**: Improvement / Major，组件 performance
- **Affects Version/s**: 无
- **Fix Version/s**: 3.2.0, **3.1.1**, 3.0.4（即已随 3.1.1 发布）
- **报告人**: Todd Lipcon（补丁亦出自其手，两版 patch 26/Jun/18、27/Jun/18）
- **性能数据**: 报告者称去掉该分配后，**TeraValidate 作业 CPU 使用率下降约 10%**。无更详细 benchmark 表格。
- **讨论要点**: 描述即全部内容——JIT 无法消除这个无用分配（对象会逃逸到 `reportCheckSumFailure` 等后续调用），所以只能手动延迟分配。

## 对 RPC 性能的影响评估

**低**（对 RPC 本身），**中**（对客户端读吞吐/GC）。

- 它不触碰 RPC 序列化、网络传输或 NameNode 处理逻辑，严格说不是 RPC 性能改动。
- 但它处于每次 HDFS 读 RPC（`readBlock` 之后的校验路径）的必经代码上，TeraValidate -10% CPU 说明在 checksum 密集（全表扫描类）负载下收益显著；对 RPC 密集但小 I/O 的场景收益有限。
