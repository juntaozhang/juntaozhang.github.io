## Diff 机制分析

**根因**：典型 AB-BA 锁序颠倒（lock-ordering inversion），涉及两把锁：
DataNode 实例 monitor（`synchronized` 方法锁）与 BPOfferService 的读写锁（ReentrantReadWriteLock）。

- **线程 1 `DataNode.refreshVolumes`**：原实现是 `private synchronized void refreshVolumes(...)`，
  一进方法就持有 DataNode monitor，方法体内又调用 `bpos.getNamespaceInfo()`
  （该方法需要 BPOfferService 的 **读锁**）→ 锁序：DataNode → BPOfferService。
- **线程 2 `BPOfferService.registrationSucceeded`**：由 register 启动流程或
  processCommandFromActor 触发的 reregister 调用，先持有 BPOfferService **写锁**
  （registrationSucceeded 在写锁保护区内），随后调用 `dn.bpRegistrationSucceeded(...)`
  需要 DataNode monitor → 锁序：BPOfferService → DataNode。

两个线程各自持有一把锁并请求对方持有的锁，死锁。触发入口是运维操作
`dfsadmin -reconfig datanode <ip:port> start`（动态增删数据目录）恰好与
DataNode 向 NN 注册/reregister 并发。

**修复方式**：

1. `refreshVolumes` 去掉方法级 `synchronized`，改为方法体内部**细粒度**的
   `synchronized(this)`：先把 `blockPoolManager.getAllNamenodeThreads()` 的
   `getNamespaceInfo()` 调用（拿 BPOfferService 读锁）挪到 **synchronized 块之外**
   完成，再进 synchronized 块做配置更新、addVolume/removeVolumes 等需要
   DataNode monitor 的操作。这样两条路径不再存在交叉锁序。
2. 作为配套测试手段，`BPOfferService.registrationSucceeded` 在持有写锁、调用
   `dn.bpRegistrationSucceeded` 之前插入 `DataNodeFaultInjector.get().delayWhenOfferServiceHoldLock()`
   注入点，配合 TestDataNodeVolumeFailure 新增用例稳定复现原死锁并验证修复。

## 影响评估

**中**。

- 死锁发生在 DataNode 侧：一旦死锁，该 DN 的 blockReport/心跳/数据读写相关
  线程逐步全部冻结，DN 从 NN 视角掉线，其上的块触发不必要的复制；
  但 NameNode 自身 RPC 服务和其它 DN 不受影响。
- 触发需要 reconfig 热加载卷与注册流程恰好并发，概率不高但属运维常见操作
  （磁盘扩容、换盘场景恰恰会并发触发 reregister）。
- 死锁后 DN 进程不死、不被自动拉起（若 systemd 无 watchdog），
  运维感知滞后，属于"挂死类"问题中影响面中等的一种。
