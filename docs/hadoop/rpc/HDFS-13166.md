## Diff 机制分析

背景：Storage Policy Satisfier（SPS，HDFS-10285 的子任务）在为文件调度 block 迁移时，**每个文件**都调用一次 `getLiveDatanodeStorageReport()`（经 NamenodeProtocol 向 NN 请求全集群 DN 存储报告）。该调用代价高：要拿 namesystem 锁、序列化全集群 storage report（响应体大）、且每次只为挑一个目标 DN。

改动：

1. **新增 `DatanodeCacheManager`**：内存缓存 `DatanodeMap`（live DN + 有剩余空间的 storage type/容量）。带可配置刷新间隔（默认 300000ms），间隔内直接返回缓存，超时才重新调用 `Context.getLiveDatanodeStorageReport()` 刷新，并缓存 `NetworkTopology`。
2. **StoragePolicySatisfier 重构**：block 搬迁调度循环改用缓存的 DatanodeMap（"fuzzy/cached state of the world"），删除了逐文件拉取报告的调用。
3. **删除 `checkDNSpaceForScheduling` RPC**：原设计在调度前逐 DN 远程校验空间，改为本地查缓存的 remaining 容量，因此从 NamenodeProtocol 中整体移除该 RPC（proto、translator、server side 全删）。这改变了 NamenodeProtocol 的接口定义（兼容方向：删除 rpc，旧客户端调用会失败，但 SPS 外部模式在 3.2.0 前不可用）。

代码路径：仅 SPS 调度线程（`StoragePolicySatisfier` 内部），与常规 DataNode/Namenode RPC 服务路径无关。

## 对 RPC 性能的影响评估

**评级：条件相关 —— 对 3.1.1 为零（SPS 功能不存在）**。

- 在启用 SPS 的 3.2.0 集群上：**高**。它把 SPS 调度的 RPC 频率从"每文件一次全集群 getLiveDatanodeStorageReport"降到"每 5 分钟一次"，且消除了逐 DN 的 `checkDNSpaceForScheduling` RPC，显著降低 NN 的 NamenodeProtocol 负载和 fsn 锁压力。
- **对 3.1.1 完全无意义**：已用 git 核实，`StoragePolicySatisfier` 类及整个 `namenode/sps` 包在 `rel/release-3.1.1` 中**不存在**（SPS feature HDFS-10285 整体在 3.1.1 之后、3.2.0 之前才合入 trunk，branch-3.1 未接收）。3.1.1 集群不可能启用 SPS，自然也没有这些 RPC 调用。

## 是否值得 cherry-pick 到 3.1.1

**不值得，也不可能**。

- 目标文件（`namenode/sps/*`、`server/sps/ExternalSPSContext.java`、`NamenodeProtocol.proto` 的 SPS 相关定义）在 3.1.1 中不存在，cherry-pick 必然全军覆没式冲突。
- 即使手工移植也毫无意义：SPS 在 3.1.1 无入口、无配置生效路径。
- 结论：从 3.1.1→3.2.0 RPC 性能 cherry-pick 清单中**剔除**。
