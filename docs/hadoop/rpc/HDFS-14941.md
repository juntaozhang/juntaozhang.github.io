# HDFS-14941 — Potential editlog race condition can cause corrupted file

## Commit

- **Hash**: `c6cbf67b82c761a3a8931eec57ff22f0e17183da`
- **Date**: 2019-11-06
- **涉及文件**: `hadoop-common/.../util/SequentialNumber.java`、`BlockIdManager.java`、`BlockManager.java`、`FSDirWriteFileOp.java`、`FSEditLogLoader.java`、`FSEditLogOp.java`、`FSNamesystem.java`、`NameNodeAdapter.java`（+测试）

## Diff 机制分析

Standby tail editlog 时 `OP_SET_GENSTAMP_V2` 直接提升全局 generationStamp，
而 Active 上真正的 genstamp 提升发生在块分配时。IBRs（增量块报告）到达
Standby 时其块 genstamp 可能"来自未来"，与 Standby 本地已提升的全局戳交错，
Active 在 allocate 时重用旧戳，导致同 stamp 不同数据、HA 切换后文件损坏。
修复：Standby 上 OP_SET_GENSTAMP_V2 只记录到新增的 `impendingGenerationStamp`
（`SequentialNumber.setIfGreater` CAS 实现）；全局 generationStamp 只在
实际收到该 stamp 的块（addBlockCollection→setGenerationStampIfGreater）或
failover 时 `startActiveServices → applyImpendingGenerationStamp` 才真正提升，
保证戳永不回退、永不复用。

## 影响评估

**高** — HA 下数据正确性：竞态可造成块 genstamp 复用、文件内容损坏，
且只在 Active/Standby 切换或 IBR 时序特定组合下触发，极难排查。核心修复必带。

## apply 检查结果

**冲突**：`NameNodeAdapter.java`（测试适配类；主代码全部 apply 干净）。
