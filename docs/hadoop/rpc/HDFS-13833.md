## Diff 机制分析

**问题**：`isGoodDatanode()` 中的 consider-load 检查是

```java
final double maxLoad = considerLoadFactor * stats.getInServiceXceiverAverage();
if (nodeLoad > maxLoad) { /* 拒绝该节点 */ }
```

当集群平均 xceiver 数为 0（例如单节点/全新集群，或平均数向下取整为 0）时，
`maxLoad = 0.0`，任何 `nodeLoad > 0` 的节点都会被以 `NODE_TOO_BUSY` 拒绝——
日志里出现荒谬的 `(load: 8 > 0.0)`，唯一可用的 DataNode 被跳过，抛
`NotEnoughReplicasException`，导致块写入/复制失败（报告人场景中 Flink checkpoint 写失败）。

**修复**：抽出 `excludeNodeByLoad(DatanodeDescriptor node)` 方法，加入
`&& (maxLoad > 0)` 条件——平均负载为 0 时不再按负载拒绝节点
（此时要么集群空载要么统计不可用，按负载挑节点没有意义）。
`isGoodDatanode()` 改为调用该辅助方法。测试新增 `testMaxLoad()`：
平均负载 0.0 + 节点 load 1 → 不排除；平均负载 1.0 + 节点 load 10（默认
`considerLoadFactor=1.2` 下 maxLoad=1.2）→ 排除。

行为变化：默认 `dfs.namenode.replication.considerLoad=true` 时，低负载/单节点集群
不再出现随机的写失败；正常多节点集群逻辑不变。

## 对 RPC 调优/排障的价值评估

**中**。

- 不属于 RPC 性能优化，但直接影响写路径的**正确性与稳定性**：块放置失败会以
  `NotEnoughReplicasException` 形式回传给客户端写 RPC，表现为随机的写失败/延迟尖刺，
  与 "RPC 抖动" 症状高度相似，极易在排障时误诊为网络或 NN 锁问题。
- 对小集群、POC、测试环境价值较高；对大规模生产集群（平均 xceiver 数远大于 0）
  几乎无感知。排障价值主要在于：遇到 `load: N > 0.0` 这类日志可以直接对号定位。
