## Diff 机制分析

**背景**：HDFS-11384 曾给 Balancer 加了 getBlocks RPC "分散"（dispersal）机制，
向 dispatch 线程池提交任务时按 `BALANCER_NUM_RPC_PER_SEC=20` 给前若干个线程
人为 sleep 1 秒，意图把 RPC 摊平到每秒 20 个。

**旧机制为什么失效**（本 JIRA 修复的核心 bug）：

- 延迟只施加给线程数组**下标靠前**的任务，而不是"正在运行的前 R 个线程"。
  线程池调度顺序与提交顺序不保证一致，先提交的带延迟任务可能后运行，
  导致实际发出的 getBlocks 仍是一窝蜂 burst。
- 更糟的是当 `concurrentThreads < 20` 时（dispatcherThreads 默认 200，
  但 concurrentThreads = min(sources, corePoolSize)，小集群/sources 少时
  经常 < 20），**没有任何线程会被加延迟**——节流功能完全失效。
- 原测试之所以没发现：统计 QPS 的窗口开得过大（从 mock DataNode 启动前
  就开始计时、横跨两次 balancer 迭代），把初始 fetch burst 平均掉了。

**修复方式**：

1. 彻底删除 Dispatcher 中的 sleep/dSec/`BALANCER_NUM_RPC_PER_SEC` 逻辑
   （净删约 34 行）。
2. 在 `NameNodeConnector.getBlocks(...)` 入口处统一加 Guava
   `RateLimiter.acquire()`——所有走 NameNodeConnector 的工具（**Balancer、
   Mover、StoragePolicySatisfier**）一次性全部被真正限速。
3. 新增配置 `dfs.namenode.get-blocks.max-qps`（默认 20，<= 0 关闭限速）。
4. 测试重写为直接观测单次 getBlocks 的 QPS（TestBalancerRPCDelay 断言
   实际 QPS 不超过上限），堵住回归。

相比旧的"提交顺序 sleep"，RateLimiter 是**运行时每线程统一排队取令牌**，
与线程池调度顺序无关，语义严格成立。

## 影响评估

**中**。

- getBlocks 是 NN 上较重的 RPC（扫描 DN 块列表、计算位置），burst 直接打到 NN
  会加剧 RPC 队列堆积和锁持有时间，对大集群 / NN 本来就吃紧的用户有实际保护价值。
- 但只在运行 Balancer/Mover/SPS 时才有影响；不跑这些工具的集群完全无感。
- 默认 20 QPS 与旧"设计值"一致，行为变化只是把"名义上限、实际失控"变成
  "真实上限"，balancer 收敛速度上限略有下降但可配置。
- 非崩溃类问题，属"NN RPC 过载风险"加固。
