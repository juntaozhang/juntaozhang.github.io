# HDFS-15219 — DFS Client will stuck when ResponseProcessor.run throw Error

## Commit

- **Hash**: `d64f6881987085acb927248730bea26d5db959d3`（branch-3.1，cherry-picked from trunk `d9c4f1129c0`，首次发布于 3.1.4）
- **Author**: Isa Hekmatizadeh（代码贡献者 zhengchenyu）
- **Date**: 2020-03-24（GitHub PR #1902）
- **涉及文件**:
  - `hadoop-hdfs-project/hadoop-hdfs-client/src/main/java/org/apache/hadoop/hdfs/DataStreamer.java`（**+1/-1**，仅此一行）

## Diff 机制分析

**根因**：`DataStreamer.ResponseProcessor.run()` 的异常捕获写的是 `catch (Exception e)`。
正常情况下 responder 线程收到 DN 的 ack 后推进 packet 序列；一旦发生 JVM 级
`Error`（典型如 `NoClassDefFoundError`——报告人案例是磁盘坏道导致 protobuf
`TextFormat` 类加载失败、zip 包读取损坏），Exception 捕获不到：

- responder 线程带着未设置的 errorState 直接死亡；
- `DataStreamer` 主线程仍在等 ack 推进/等 pipeline 恢复，检测不到 responder 已死，
  也不会触发 `closeResponder`/错误上报路径；
- 写操作的 DFSOutputStream 调用线程（应用侧）无限阻塞——DFS Client 挂死。

**修复方式**：把 `catch (Exception e)` 改为 `catch (Throwable e)`，
让 Error 也走统一的错误处理：`lastException.set(e)`、
`errorState.setInternalError()`、唤醒等待的 streamer 主线程并以异常结束写。
改动虽只有一行，但把"线程无声死亡"变成"显式错误传播"。

## JIRA 页面信息

- **Affects Version/s**: 2.7.3（2.7 起该代码即如此，3.x 全系列含 3.1.1 未修复）
- **Fix Version/s**: **3.1.4**, 3.2.2, 3.3.0
- **Priority**: Major
- **报告人/Assignee**: Chenyu Zheng（zhengchenyu）
- **触发场景**：生产案例为 Tez 任务挂死超 2 小时（speculation 关闭时表现为
  task attempt 卡死）。根因链：磁盘错误 → 读取 jar/zip 出错 →
  `NoClassDefFoundError: com.google.protobuf.TextFormat` →
  ResponseProcessor 只 catch Exception 未设 errorState → client stuck。
  报告人用单测验证：在 ResponseProcessor.run 中人为抛 NoClassDefFoundError，
  `TestDataStream.testDfsClient` 因超时而失败。
- **报告人原话**："ResponseProcessor.run only catch Exception, can't catch
  NoClassDefFoundError. So the ReponseProcessor didn't set errorState."

## 影响评估

**中**。

- 影响的是 HDFS 客户端（写路径）而非 NN RPC 服务：单个 client 挂死，
  服务端 NameNode/DataNode 均正常。
- 但挂死形态恶劣：应用线程无限阻塞（无超时、无异常），在 YARN/Tez/Spark
  等长作业里会直接拖死 task/container，排查成本高（需要 jstack 才能定位）。
- 触发需要底层 Error（类加载失败、OOM 之外的 linkage error 等），
  频率不高，多与磁盘/部署环境故障叠加出现。

## 是否值得 cherry-pick 到 3.1.1

**值得（低成本，建议顺手 pick）**。

- 单行改动，经 `git apply -3` 实测**干净应用**到 3.1.1，零冲突风险。
- 语义明确：捕获 Throwable 后进入既有的错误上报路径，不改变正常路径行为。
- 对运行 3.1.1 且跑计算框架（Hive/Tez/Spark）的集群，可避免一类
  "任务莫名挂死、只能杀 task" 的运维痛点。
