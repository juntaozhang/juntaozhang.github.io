## Diff 机制分析

**根因**：启用 `dfs.namenode.edits.asynclogging`（默认开启）时，FSEditLogAsync 的
`enqueueEdit()` 原实现是 `offer(edit, 1, SECONDS)` 超时后退回阻塞式 `editPendingQ.put(edit)`。
问题在于 `logEdit`/`logSyncWait` 整个调用链运行在 `synchronized (FSEditLogAsync)` 内
（JIRA 栈显示触发点包括 `DelegationTokenSecretManager.logExpireToken` 的 token 过期线程、
`rollEditLog` 线程、IPC handler 线程）。当 async 消费线程（`logSync`）处理慢、
默认容量 4096 的 `editPendingQ` 被填满时：

- 生产者线程在持有 `FSEditLogAsync` monitor 的情况下 park 在 `ArrayBlockingQueue.put()` 上；
- 而消费线程 `FSEditLogAsync.run()` 执行 `doEditTransaction` 恰恰需要先获得同一个
  `FSEditLogAsync` monitor —— 双方都等对方释放锁，**死锁**。

一旦死锁，所有走 FSEditLog 的元数据写操作（create、delete、token 操作、HA 的 rollEditLog）
全部冻结，NameNode 事实上宕机（但进程不死、ZKFC 不一定能探测）。

**修复方式**（Daryn Sharp 重写 enqueue 的溢出路径）：

1. 快路径仍是 `editPendingQ.offer(edit)`，无锁竞争、无超时轮询，不影响正常性能。
2. 队列满时区分两种调用者：
   - **已持有 `this` monitor 的线程**（`Thread.holdsLock(this)`）：绝不能阻塞式 put
     （那正是死锁根源），改为 `this.wait(1000)` 循环 + 重试 offer，主动让出 monitor；
     同时用自定义 `Semaphore overflowMutex`（drainPermits 做高优先级预留）防止
     大量同步调用者惊群。
   - **未持有 monitor 的线程**：用 `overflowMutex.acquire()` 限流后 `put()`，避免
     多线程在满队列上空转竞争。
3. `editPendingQ.put` 失败重试期间会收到 logSync 完成的 notify（每次 logSync 后
   `notifyAll`），所以 wait 循环必然能推进。

测试 `TestEditLogRace` 增加了在满队列 + rollEditLog 场景下的回归用例。

## JIRA 页面信息

- **Affects Version/s**: 2.7.5（async editlog 自 2.7 引入，3.x 全部受影响，3.1.1 未含修复）
- **Fix Version/s**: 2.8.6, 2.9.2, 2.10.0, 3.0.4, **3.1.2**, 3.2.0
- **Priority**: Major（labels: AsyncEditlog, deadlock）
- **报告人**: zhangwei；Assignee: Daryn Sharp
- **触发场景**：async editlog 滚动（rollEditLog / token 批量过期）期间消费端慢，
  edit queue（默认 4096）被填满即可能死锁。JIRA 附带的线程栈展示了三线程互等
  （token 过期线程持锁 park 在队列 put 上、FSEditLogAsync 线程等 monitor、
  IPC handler 同样持锁 park）。
- **关联**: HDFS-13112（Token expiration edits may cause log corruption or deadlock，
  Critical）——token 过期批量写 edit 是主要放大器，本 JIRA 修了其中的死锁面。

## 影响评估

**高**。

- 直接冻结 NameNode 全部写 RPC：死锁后 namenode 不再响应任何元数据写，
  客户端表现为 RPC 无限排队/超时，比进程崩溃更糟（监控难以发现，需 jstack）。
- 触发条件（edit queue 打满 + rollEditLog/token 过期）在大集群、RPC 高峰期、
  SNN/observer 拉取慢叠加时并非罕见；HDFS-13112 说明社区在 3.1 时代已观察到
  相关生产事故。

## 是否值得 cherry-pick 到 3.1.1

**值得，强烈建议**。

- 主代码（FSEditLogAsync.java）经 `git apply -3` 实测**可干净应用到 3.1.1**；
  仅测试文件 TestEditLogRace 在官方 cherry-pick 时就报过冲突（上游已解决，
  3.1 分支自带版本能干净应用）。
- 改动自包含、风险低：正常路径行为不变（仍是 lock-free offer），只重写溢出路径。
- 不 pick 的话，运行 3.1.1 的 NN 在 edit queue 满 + 滚动时存在整体挂死风险。
