# HDFS-10240 — close/recoverLease 竞态导致块丢失

## Commit

- **Hash**: `865650052b0`（branch-3.1，2018-08-16，Jinglun / zhouyingchao / Wei-Chiu Chuang）
- **涉及文件**（6 个，+88/-1）：`BlockInfo.java`、`BlockManager.java`、`BPServiceActor.java`、`DataNode.java` + 2 测试文件

## Diff 机制分析

客户端 `close()`（`complete` RPC，提交最后一块）与租约超时触发的 `recoverLease` 并发时：

1. `recoverLease` 把最后一块置为 `UNDER_RECOVERY`，完成恢复后块可能以较小长度 complete；
2. 与此同时 `commitOrCompleteLastBlock` 拿着**更早**的 commitBlock 继续走 commit 流程——原代码不检查 UNDER_RECOVERY 状态，把恢复中的块直接 commit 成另一个状态/长度，两个流程互相覆盖，最终**块内容与文件长度不一致甚至块从管道记录中丢失**（missing block，数据已写但 NN 认为没有）。

修复：`commitOrCompleteLastBlock` 里若 `lastBlock.isUnderRecovery()` 直接抛 IOException（让客户端重试，此时 recoverLease 流程将完成块）；`BlockInfo` 新增 `isUnderRecovery()`。另含测试辅助（`areIBRDisabledForTests`，IBR 节流开关，用于测试稳定复现竞态）。

代码路径：客户端 `close()` → `ClientProtocol.complete` → `FSNamesystem.completeFile` → `BlockManager.commitOrCompleteLastBlock`；与租约 monitor 的 `recoverLease` 并发（NN 写锁热路径竞态）。

## 影响评估

**评级：高**。直接造成数据可见的 missing block（写入的数据"丢了"），是 HDFS 最严重的正确性 bug 之一；HBase/Hive 高并发写 + lease 回收场景可触发。
