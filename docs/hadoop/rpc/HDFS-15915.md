# HDFS-15915 — Race condition with async edits logging due to updating txId outside of the namesystem lock

## Commit

- **Hash**: `49490af23c7`
- **日期**: 2021-05-26
- **涉及文件**: `EditLogOutputStream.java`、`FSEditLog.java`、`FSEditLogAsync.java`、`JournalSet.java`（主代码）；`NameNodeAdapter`/`TestEditLogRace`/`TestObserverNode`/`HATestUtil`（测试）

## Diff 机制分析

核心是把 txid 的分配/记录收回到 `FSEditLog.logEdit` 的 synchronized 临界区内：

1. `beginTransaction(op)` 提前到 `doEditTransaction(op)` 之前、在持锁状态下执行，`op.setTransactionId(txid)` 与 `txid++` 原子完成；`doEditTransaction` 内改为 assert op 已带 txid。
2. `EditLogOutputStream` 新增 `getLastJournalledTxId()`，由 `JournalSet` 统一跟踪各底层流实际已写入的最后一个 txid；`logSync` 计算 `editsBatchedInSync` 时改用 `lastJournalledTxId` 而不是全局 `txid` 计数器——避免异步写场景下用"已分配但未落盘"的 txid 误判批次范围。
3. `myTransactionId` ThreadLocal 初始值从 `Long.MAX_VALUE` 改为 `0`：没产生事务的 RPC 线程在 `logSync` 时因 `mytxid <= synctxid` 直接退出，不再参与无谓的 sync 等待。

## 影响评估

**高**。这是 FSEditLogAsync（HDFS-12943 引入的异步 edit log）的配套正确性修复：txid 在锁外更新会造成 logSync 基于错误的 txid 范围做 flush，极端情况下造成 edit log 空洞/错位，影响主备一致与故障恢复。跑 HA + 异步 edit log 的 3.1.x 集群应合入。
