## Diff 机制分析

`chooseRandom(...)`（块放置策略核心路径，addBlock/复制/EC 选 DN 都会走到）
开头原代码：

```java
StringBuilder builder = null;
if (LOG.isDebugEnabled()) {
  builder = debugLoggingBuilder.get();   // 只有进方法时是 debug 才初始化
  builder.setLength(0);
  builder.append("[");
}
```

方法体内后文有 4 处 `builder.append(...)` / `builder.toString()`（拼接"选了哪个 DN /
为什么不选"的调试信息，最终在 `NotEnoughReplicasException` 里带出）。

**崩溃机制**：运行中的 NN 用 `hdfs daemonlog`（或 log4j 动态开关）把
BlockPlacementPolicyDefault 的 logger 调到 DEBUG。若 chooseRandom 进方法时还是
INFO（builder = null），执行中途 logger 级别翻成 DEBUG，后文判断
`LOG.isDebugEnabled()` 变为 true 而 builder 仍为 null → NPE 抛出。
该方法运行在 FSNamesystem 写锁保护区内，NPE 一路抛出可导致 NameNode 崩溃。

**修复**：`builder` 不再以 null 初始化，而是无条件从 ThreadLocal 取：

```java
StringBuilder builder = debugLoggingBuilder.get();
if (LOG.isDebugEnabled()) {
  builder.setLength(0);
  builder.append("[");
}
```

builder 永不为 null，级别中途翻转最多导致调试信息拼接不完整，不会 NPE。

**配套测试**：新增 `TestBlockPlacementPolicyDebugLoggingBuilder`，用 mock 的
`chooseDataNode` 在 chooseRandom 执行**中途**把 `BlockPlacementPolicy.LOG`
级别从 INFO 翻成 DEBUG，复现并锁定该场景。

**对 3.1.1 的重要核实（本验证的关键发现）**：
同样的 NPE 场景早在 **HDFS-11827**（`ec21ce425f4`，2017）就用
`LOG.isDebugEnabled() && builder != null` 双条件守卫修过一次，且 **HDFS-11827
已在 rel/release-3.1.1 中**——已逐一核对 3.1.1 的 chooseRandom，全部 4 处后续
使用点都带 `builder != null` 守卫，子类（RackFaultTolerant / WithNodeGroup）
不触碰 builder。因此报告人在 JIRA 中描述的精确 NPE 在 3.1.1 上**已被守卫挡住**，
其崩溃很可能发生在缺少 HDFS-11827 守卫的构建上（该修复也随 2.10.1 发布）。
不过本修复仍有一份额外价值：debug 中途打开时，方法开头没做 `setLength(0)`，
`logNodeIsNotChosen()` 会往 ThreadLocal builder 追加内容却无复位，
长期运行存在跨调用内容累积的隐患；修复后 builder 恒非空、状态可控。

## 影响评估

**低**（针对 3.1.1 用户）。

- 3.1.1 已含 HDFS-11827 的 `builder != null` 守卫，JIRA 所述 NPE 直接触发路径
  已被覆盖；实际剩余风险仅为 ThreadLocal builder 状态累积一类弱隐患，
  不会导致 NN 崩溃。
- 触发条件本身苛刻：需要运维在 NN 运行时对该类开 DEBUG，且恰逢块放置正在执行。
- 对 NN RPC 无直接影响（属 NN 内部块放置路径的健壮性加固）。
