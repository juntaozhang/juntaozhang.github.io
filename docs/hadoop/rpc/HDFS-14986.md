# HDFS-14986 — ReplicaCachingGetSpaceUsed throws ConcurrentModificationException

## Commit

- **Hash**: `f1a19b7a3f590f8b1876deb1bae6dfb4bf840edb`
- **Date**: 2019-11-28
- **涉及文件**: `hadoop-common/.../fs/CachingGetSpaceUsed.java`、`hadoop-hdfs/.../fsdataset/FsDatasetSpi.java`、`FsDatasetImpl.java`、`fsdataset/impl/ReplicaCachingGetSpaceUsed.java`（+测试）

## Diff 机制分析

根因是 DN 磁盘用量统计的三处缺陷叠加：

1. `CachingGetSpaceUsed.init()` 在 `used<0` 时同步执行一次 `refresh()`（全量 du 扫描），
   DN 启动时每个 volume 都阻塞一次；修复后新增 `shouldFirstRefresh` 标志，
   `ReplicaCachingGetSpaceUsed` 置 false，跳过启动期同步刷新，改为 refresh 线程
   启动后立即执行（`runImmediately`），启动提速。
2. `FsDatasetImpl.deepCopyReplica()` 之前刻意不加 datasetLock（注释称防与
   `FsVolumeList.addBlockPool` 死锁），导致 refresh 线程与 block 增删并发遍历
   `volumeMap.replicas(bpid)` 的 HashSet，抛 ConcurrentModificationException。
   修复改为用 `datasetLock.acquire()` 加 AutoCloseableLock 拷贝。
3. `FsDatasetSpi` 补上 deepCopyReplica 的 javadoc。

## 影响评估

**低** — 修的是 DN 空间统计后台线程的并发正确性与启动期一次全量扫描；CME 只影响
du 统计线程的本次刷新（下次重试），不影响数据读写 RPC，但修复后 DN 冷启动明显更快。
