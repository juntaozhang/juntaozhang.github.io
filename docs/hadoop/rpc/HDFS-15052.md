# HDFS-15052 — WebHDFS getTrashRoot leads to OOM due to FileSystem object creation

## Commit

- **Hash**: `8095e3b149f2a4b7bab06fb038084bffda57563e`
- **Date**: 2020-02-21（GitHub PR #1758）
- **涉及文件**: `DFSUtilClient.java`、`DistributedFileSystem.java`、`NamenodeWebHdfsMethods.java`（+测试）

## Diff 机制分析

WebHDFS 处理 `GETTRASHROOT` 时，NN 端 Jersey 资源 `getTrashRoot()` 调用
`FileSystem.get(conf)` 创建一个 DistributedFileSystem 实例只为计算 trash 路径。
WebHDFS 请求以 doAs 执行，每个用户/每次调用都新建 FileSystem（含 Kerberos/ugi
上下文、连接缓存等），高频调用下 FileSystem 对象堆积导致 NN 堆压力/OOM。
修复：NN 端不再建 FileSystem，直接通过已有 RPC 通道 `getEZForPath` 判断加密区，
trash 路径改为 `DFSUtilClient.getTrashRoot/getEZTrashRoot` 纯字符串计算；
`getHomeDirectory` 返回类型由 Path 改为 String 避免无谓对象。

## 影响评估

**中** — 内存/GC：依赖 WebHDFS 且用户多、调用 getTrashRoot 频繁（如 Hive/Spark
作业查询 trash 根）的集群有真实 OOM 风险；修复在 NN 服务端热路径上消除了
每次请求的 FileSystem 创建。
