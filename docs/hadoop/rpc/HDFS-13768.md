## Diff 机制分析

DataNode 启动时 `BlockPoolSlice.getVolumeMap()` 需要把磁盘上的 block 文件递归扫描并加入 `ReplicaMap`。改动前这是单线程递归（每个 volume 一个线程，但 volume 内串行），且 `FsDatasetUtil.getGenerationStampFromFile` 对每个 block 文件都要在目录列表中线性查找对应 meta 文件（O(n²) 的字符串前缀匹配 + canonical path 比较）。

改动内容：

1. **ForkJoinPool 并行扫描**：新增静态 `addReplicaThreadPool`（大小默认为 `max(volume数 × bp_service数, CPU核数)`，可由 `dfs.datanode.volumes.replica-add.threadpool.size` 覆盖）。`getVolumeMap` 对 finalized 目录和 rbw 目录各提交一个 `AddReplicaProcessor`（RecursiveAction），遇到子目录就 `fork()` 子任务并入 `ConcurrentLinkedQueue`，父任务最后逐个 `join()` 等待。volume 内扫描由串行变为并行。
2. **meta 文件查找 O(n²)→O(1)**：目录列表先按文件名排序，`getGenerationStampFromFile` 从"全列表扫前缀"改为直接检查 `files[i+1]`（block 文件排序后 meta 文件紧随其后），消除了 canonical path 解析开销。
3. **并发安全的 map 插入**：`ReplicaMap` 新增 `addAndGet()`（一次锁内完成查重+插入），替代原来"get 一次、add 一次"两次取锁；`addReplicaToReplicasMap` 改为用它处理并行插入时的重复 block 裁决（`resolveDuplicateReplicas`）。

代码路径：DataNode 启动 → `FsDatasetImpl` 构造/`registerMBean` 前的 volume 扫描 → `BlockPoolSlice.getVolumeMap()`（仅 cache miss 时）。

## JIRA 页面信息

- **Affects**: 3.1.0；**Priority**: Major；**Reporter**: Yiqun Lin
- **背景**：滚动升级中 DataNode 启动缓慢，无法及时向 NameNode 注册，DataXceiver 处理 WRITE_BLOCK 时反复抛 "Not ready to serve the block pool"。jstack 显示线程阻塞在 native 目录列举（`UnixFileSystem.list`）。
- **性能数据**：每个 volume 扫描耗时 242s–287s（日志原文 `/home/hard_disk/1/dfs/dn/current: 242722ms`、`287235ms`），即单 volume 4–5 分钟，多盘机器启动时间被最慢盘拖住。
- **讨论**：13 个 patch 迭代（.01 ~ branch-2.03）。已知后续问题 **HDFS-14251**：此修复引入的 ForkJoinPool 在 Java SecurityManager 下会 break（该 issue 至今 Open）——若集群启用 SecurityManager 需注意。
- 关联：HDFS-13962（本修复的 follow-up bug fix）。

## 对 RPC 性能的影响评估

**评级：低（间接、启动期）**。这是 DataNode 启动加速，不是 RPC 路径优化。间接收益：DN 更快注册并进入可服务状态，缩短了升级/重启期间 `WRITE_BLOCK`/`blockReport` 等 RPC 失败重试的窗口，改善了重启场景的 RPC 成功率与尾延迟。对稳态 RPC 吞吐/延迟无影响。
