## Diff 机制分析

Standby NN 用 `EditLogTailer` 周期触发 active 滚动 edit log（`dfs.ha.log-roll.period`，默认 120s）以便 tail finalized 段。

原逻辑 `tooLongSinceLastLoad()` 用 `lastLoadTimeMs`（上次**成功加载** edits 的时间）判断"太久没 roll 就再触发一次"。开启 in-progress 段 tailing（`dfs.ha.tail-edits.in-progress`）后，tailer 频繁从 in-progress 段读到新事务，`lastLoadTimeMs` 不断更新 → 永远不满足"太久没 roll" → **standby 不再触发 log roll**。如果 active 的 `autoroll.multiplier.threshold`（2.0）也满足不了（日志量小），edit log 段一直不 roll、不 finalize → SNN 永远等不到 finalized 段 → **永远不产生 checkpoint**，edit 日志无限增长。

修复：

1. 新增独立的 `lastRollTimeMs`，`tooLongSinceLastLoad` 改为基于"上次触发 roll 的时间"判断；
2. `triggerActiveLogRoll` 成功后在 RPC future 返回时更新 `lastRollTimeMs`；
3. active 侧 autoroll 阈值默认从 2.0 收紧为 0.5，保证小流量集群也定期 roll。

代码路径：SNN `EditLogTailer$EditLogTailerThread.run`（每 1s 检查）→ `triggerActiveLogRoll` RPC 到 active NN。

## 影响评估

**评级：中**。影响启用 in-progress tailing 的 HA 集群的 checkpoint 及时性，edits 无限增长会拖慢故障恢复并占满磁盘；属于 HA tailing/checkpoint 正确性修复。注意与已 reverted 的 HDFS-13813（FSImage 修复）无冲突关系，但同样动 EditLogTailer，合入时注意上下文。
